# Ревью главы Algo Patterns

Проводи независимое read-only ревью существующей главы и сообщай только выводы, подтверждённые текущими файлами и выполненными проверками.

## Объект и граница

- Проверяй активный git checkout, полученный через `git rev-parse --show-toplevel`; не подменяй его захардкоженным основным checkout.
- Локальный источник Educative по умолчанию: `/Users/user/projects/blog/Educative.io - Grokking the Coding Interview - Patterns for Coding Questions` (только чтение). Если он недоступен, явно ограничь выводы о покрытии и переводе.
- `_data/notes/algo.md` содержит отправные внешние ссылки, но не готовое отображение задач.
- Не исправляй статьи, ссылки или код без явного запроса. Временные каталоги для компиляции и сборки допустимы.

Зафиксируй проверяемое состояние (`git status`, текущий commit при наличии и список файлов объекта), чтобы не смешивать наблюдения до и после чужих изменений.

Перед исполнением или делегированием прочитай [golden example](references/golden-example.md). Он показывает границы targeted review и доказательный отчёт, но не задаёт ожидаемый verdict текущей главы.

## Выбери объём

Проверяй только измерения, указанные пользователем. Полный аудит выполняй, когда пользователь прямо просит полное/комплексное ревью или перечисляет все измерения.

- **Покрытие и перевод:** основная статья, все субпосты того же `pattern` и полная соответствующая папка Educative, включая challenge/solution review.
- **Go:** только Go-блоки выбранной главы; структура программы, соответствие алгоритму и сложности, примеры и релевантные границы.
- **Jekyll и навигация:** front matter, единственность родителя `pattern`, сортировка, permalink, якоря, верхняя/нижняя навигация и видимость коллекции.
- **Иллюстрации:** соответствие исходнику, локальные файлы, SVG/XML, размеры, `alt`, загрузка и переполнение.
- **Внешние ссылки:** соответствие задачи первичной странице, а не только HTTP-статус. `Похожие задания` не доказывают покрытие Educative.

Всегда читай `AGENTS.md`. `_config.yml` и `_includes/algo-task-nav.html` нужны для Jekyll/навигации или когда их поведение влияет на другой проверяемый вывод; не загружай их ритуально для несвязанного точечного ревью.

## Доказательства

- Для покрытия составь карту `исходная задача → основная статья | субпост | отсутствует | дубль`. Не считай технические страницы источника отдельными задачами.
- Для перевода сопоставь условия, ограничения, примеры, порядок алгоритма, особые случаи и сложности. Не объявляй стилистическое отличие ошибкой перевода без смыслового расхождения.
- Для каждого проверяемого Go-блока выполни `gofmt` и `go run` в отдельном временном каталоге. Дополнительные тестовые вызовы не должны изменять статью. Успех одного примера не доказывает корректность границ.
- Для сборки сначала проверь `ruby -v`, `bundle -v`, `bundle check`. Используй уже установленный совместимый Ruby; не устанавливай глобальные зависимости без разрешения.
- Jekyll собирай с `--future` в новый destination из `mktemp -d`. HTML-Proofer запускай для этого destination с опциями внутренних ссылок из CI/Makefile. Существующие предупреждения отделяй от регрессий.
- Визуальные свойства подтверждай браузером на релевантных ширинах; успешная сборка HTML их не доказывает.

Если проверку нельзя выполнить, зафиксируй точную ошибку и сузь вывод. Не превращай план проверки или старый результат в доказательство.

## Результат

Начинай с findings по убыванию серьёзности. Для каждого укажи приоритет `P0`–`P3`, файл и строку, наблюдаемое расхождение, влияние, минимальное направление исправления и доказательство.

После findings перечисли только реально проверенные измерения и их ограничения. Таблицу покрытия добавляй только при проверке покрытия; таблицу Go — только после запусков; Jekyll/HTML/визуальный блок — только для выполненных проверок. Если findings нет, прямо скажи это без общего одобрения непроверенных областей.
